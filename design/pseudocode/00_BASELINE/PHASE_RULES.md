> 依据：`ResearchFlow_伪代码阶段_10阶段执行提示词_v1.1` 的 S0 与 0.5 节。

> 修订：2026-11-11｜v1.1 → v1.2：新增 §4.4「例外：用户明令的收尾」，区分轻收尾与重收尾，解决 §4.2 与 `memory-handoff` 的冲突；§4.2 原文未改。

## 1. 阶段定位

本阶段产出「可评审、可追溯的伪代码规格」，位于 `design/pseudocode/`。

- 不是可运行代码，不进 `researchflow/`，不建 `.venv`，不装依赖，不建库，不部署。
- 不是 G0 规格的替代品：`contracts/`、`docs/design/`、`docs/ADR/` 是上游冻结件，本阶段只引用、对齐、登记缺口。
- 本阶段的产出服务于 T0 施工（WP-03 起），不改变施工顺序与门禁。

## 2. 权威顺序

冲突时逐级降级，越级必须登记 OPEN QUESTION：

1. 用户当轮的明确指令；
2. 策划书 DOCX 正文（内部标示 v4.3.0；文件名标签 v4.3.1）；
3. `contracts/`、`docs/design/05`–`06`、`docs/ADR/` 等 G0 冻结件；
4. 本文件（PHASE-RULES）与已验收阶段的 `MODULE.md`；
5. 既有提示词包（续接包 v2.1、10 阶段提示词 v1.1）；
6. 通用工程经验。

第 6 级不得覆盖前 5 级。

## 3. 五条不可越界的可信边界

任何阶段的伪代码都不得设计出下列路径：

1. E0（Agent 声明）不得推动任务状态，也不得满足执行类必检项；
2. E2 只由 Collector 观测受控执行产生，Agent 与 Adapter 均不得生成；
3. E3 只由独立 Verifier 产生，Verifier 与 Executor 工作目录分离；
4. L3 必须在新目录、独立进程、从原始数据真实重训或重推；
5. 只有 `final_state = VERIFIED` 的报告才允许签发 CompletionCertificate。

## 4. 产出与限权

### 4.1 允许写

- `design/pseudocode/**`（本阶段唯一写入面）。

### 4.2 禁止写

| 禁止 | 说明 |
|---|---|
| `contracts/**` | 五份 schema 与 72 个正反例已冻结，只读 |
| `docs/design/**`、`docs/ADR/**` | G0 冻结件，只读 |
| `researchflow/**` | 实现代码，本阶段不碰 |
| `docs/state/project_state.json`、`IMPLEMENTATION_STATUS.md`、`CHANGELOG_DEV.md` | 施工态看板，不因伪代码阶段而变 |
| Git 提交 | 由用户决定何时提交 |

### 4.3 禁止动作

创建 `.venv`、安装或升级依赖、运行 `pytest`/`unittest`、调用真实 Verifier、执行模板、联网抓资料。

允许的语法自检仅限 `ast.parse`（不导入、不执行、不产生副作用）。

### 4.4 例外：用户明令的收尾

§4.2 的禁令针对**单阶段执行期间**，防止边写伪代码边改看板。以下两种情形由用户明令发起，不受 §4.2 限制：

| 情形 | 允许写 | 必须遵守 |
|---|---|---|
| **轻收尾**（每个 P 阶段结束） | `design/pseudocode/` 内的日志与索引 | 只追加，不改历史；不碰 `docs/` 任何文件 |
| **重收尾**（里程碑或 WP 验收后） | `docs/state/`、`CHANGELOG_DEV.md`、`SESSION_HANDOFF.md`、`docs/memory/*` | 必须走 `researchflow-memory-handoff` 的 9 步；`state_sync` 三步全 exit 0 才可宣称同步 |

判定方法：**本轮任务是不是用户显式要求的收尾？** 是则按上表；否则一律按 §4.2 拒绝。

## 5. 文件规范

- 目录：`design/pseudocode/M<两位序号>_<slug>/`，基线目录 `00_BASELINE/`。
- 每个 `.py` 首部固定 6 行注释块：MODULE / 阶段+追踪 / FR+依赖 / 不变量+错误码 / 写入者 / 状态。
- 每个函数：类型标注 + docstring（职责、输入、输出、副作用、不变量、错误）+ 编号中文步骤函数体。
- 每个判定分支必须有明确 `return` 或 `raise`，每个 `raise` 使用已注册错误码。
- 库调用只写意图并标 `# LIB:`，不写真实路径、真实哈希值、真实密钥。
- **行数不是验收指标。文件按「职责单元」组织，不按行数组织。**
  1. ≤ 800 行：无需额外动作。
  2. 800–1500 行：必须在该模块 `MODULE.md` 的「文件导航」节登记完整函数索引，
     逐行给出：类/函数名 → 起始行 → 职责一句话 → 依据章节（05/06 的节号）。
     本档不要求拆分，也不要求解释理由。
  3. > 1500 行：除索引外，还必须在 `MODULE.md` 写明「本文件包含的职责单元清单」+
     「不拆的理由」或「拆分方案」，并登记进 `OPEN_QUESTIONS.md` 由用户裁决；
     未裁决不阻塞阶段验收，但必须挂表。
  4. 两种行为一律禁止：
     - 为满足行数上限而拆分、合并、压缩、省略、写「以下略」；
     - 为省事把多个职责塞进一个文件（判断依据是职责数，不是行数）。
  5. 生效与追溯：本规则自 P3 起执行。P1/P2 已落盘文件不返工、不改内容，
     只需按第 2 档对「超过 800 行」的文件补登索引，共 3 个：
     `state_machine.py` ≈1.3k、`transitions.py` 926、`schema_sql.py` 835。
     其余 6 个（`errors.py` 537、`schemas.py` 403、`boot_recovery.py` 495、
     `invariants.py` 482、`migrations.py` 455、`repositories.py` 596）≤ 800 行，无需动作。
  6. 本文件（PHASE-RULES）头部版本 v1.0 → v1.1，并加一行修订记录：日期、改了什么、依据本裁决。
- 每模块固定产出 `MODULE.md` 与 `NEGATIVE_TESTS.md`；负例至少 8 条，每条写明「拒绝点 → 期望错误码/状态」。

## 6. 继续协议

单轮写不下时：不许删减、不许「以下略」、不许合并函数；在断点写 `CONTINUE-FROM: <下一个文件或函数>`；续写完成后输出 `STAGE-COMPLETE: P<k>`。

## 7. 技能调用与限权

- 按阶段调用 2–3 个，不全量注入（`AGENTS.md` 第 36 行）。
- **只取**：检查表、判定规则、禁止清单。
- **不执行**：技能里的建环境、跑测试、改看板、写业务代码步骤。
- 技能不可用时记 `SKILLS-UNAVAILABLE`，继续按阶段验收判据执行。

## 8. 未决问题

统一登记在 `design/pseudocode/OPEN_QUESTIONS.md`：纯索引表，每个 OQ 一行，列为
「OQ 编号 / 一句话问题 / 提出阶段 / 状态 / 死线 / 裁决·结论 / 落点（文件 §）/ 阻塞谁」。

- 状态只允许 `OPEN` / `DEFERRED` / `DECIDED` / `NEEDS_CONFIRMATION` 四个值。
- `NEEDS_CONFIRMATION` 仅用于“曾声称已裁决，但原问题或裁决正文/证据不可恢复”的条目；它不等于 `OPEN`，也不得当作 `DECIDED`，更不得作为后续阶段先例。
- 已有编号原样沿用；无编号项写 `(无编号) §12-N`，靠「落点」列定位，不新造编号。
- 裁决结果写入对应模块 `MODULE.md` 的 `DECISIONS` 段或对应节，并保留原 OQ 编号以便追溯。
- P3 起每个阶段收尾必须新增/更新本表并报告行数变化；未更新本表的阶段不算完成。
