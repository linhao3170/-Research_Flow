## 2. 失败经验与教训

### L-01 终端代码页会破坏中文 DOCX 抽取结果

- 现象：直接用 PowerShell 捕获 Python 输出的中文标题，出现乱码。
- 原因：控制台代码页与 Python 输出编码不一致。
- 处理：把抽取结果以 UTF-8 写入临时文件，再用支持 UTF-8 的读取工具查看。
- 教训：涉及中文文本的脚本应显式 `encoding="utf-8"`；日志与生成文件统一 UTF-8。

### L-02 DSH 的 AGENTS 刷新是“触碰驱动”的

- 现象：重写 `AGENTS.md` 后，当前会话立即收到 `Updated instructions from: AGENTS.md`，内容为新版本。
- 原因：`agent-instructions` 在成功的 `read` / `write` / `edit` 后检查变更；没有文件监听器。
- 教训：修改 AGENTS 后应主动读取或写入同一路径以触发刷新；不能假设“文件已改 = 模型已看到”。

### L-03 生成的文档会漂移

- 风险：手工编辑 `docs/PROJECT_STATE.md` 或 `docs/IMPLEMENTATION_STATUS.md` 后，与 JSON 不一致。
- 处理：`state_sync.py check` 按字节比较；不一致返回非零；文件头写明“自动生成，请勿手工编辑”。
- 教训：状态只改 JSON；生成文件只读；CI/验收先跑 `validate`，再跑 `render`，最后跑 `check`。

### L-04 空任务数组是合法状态，不要为了“好看”编造任务

- 现象：阶段 4 只有治理工作，没有 ResearchFlow 研发任务。
- 处理：`tasks: []`；G0–G7 全部 `NOT_STARTED`；在 CHANGELOG 记录治理工作，不写入研发看板。
- 教训：状态文件的空白比虚假进度更有价值；不能用“看起来有进展”替代真实证据。

### L-05 两套状态词汇极易混淆

- 风险：把研发看板的 `IN_REVIEW` / `DONE` 当成运行时 Task 状态，或把运行时 `VERIFYING` 写进研发看板。
- 处理：`project_state.json` 的枚举只允许 `BACKLOG`…`DEFERRED`；运行时状态单独文档化。
- 教训：Schema 校验必须拒绝跨词汇取值；文档与代码都要用不同命名空间。

### L-06 “本会话批准”不等于“提交批准”或“下一阶段批准”

- 现象：用户批准阶段 4 执行，但明确要求不得自动 commit，报告后停止等待阶段 5。
- 处理：完成阶段 4 后只报告，不 `git add` / `git commit`，不进入阶段 5。
- 教训：批准范围按任务和阶段理解，不做扩大解释。

### L-07 实际运行版本可能不同于 profile 里的 npm 包版本

- 现象：桌面壳是 `0.2.2-rc.1`，但 `.dsh/profiles/node_modules/@deepseek-ai/dsh` 是 `0.1.0-rc.8`。
- 风险：直接引用旧包的 README/配置，会把旧行为当成当前行为。
- 处理：阶段 5 从 `app.asar` 内 `0.2.2-rc.1` 的 provider 源码核实 `.agents/skills`，再用实际 catalog 刷新与 `skill` 加载验证。
- 教训：版本相关结论必须同时记录“安装路径 + 版本 + 实际运行结果”，不能只看某个 node_modules。

### L-08 禁用一个通道不等于禁用同类能力

- 现象：阶段 2C 将 `web-fetch-http` 设为 `disabled: true`，但 MCP Client 是独立的 Cordis 插件与传输通道。
- 风险：把“web_fetch 工具不可用”当成“所有外部文档能力不可用”，从而错误地判定 MCP 必须 DEFERRED。
- 处理：阶段 6 分别核实：`web_fetch` 保持禁用；`dsh-mcp-client` 从 app.asar 源码与 Context7 端点单独验证。
- 教训：能力判断必须落到具体 provider / 插件 / 端点，不能用相邻通道的状态替代。

### L-09 文件名的版本号可能只是打包标签

- 现象：文件名写 `v4.3.1`，但文档封面、页眉、正文升级说明、core 属性标题全部写 `v4.3.0`；文档内 `v4.3.1` 字符串计数为 0。
- 风险：若直接把文件名当基线，会把不存在的“v4.3.1 内容”写进 G0 契约与验收材料。
- 处理：阶段 7 全文抽取后登记 `C-001`；`BLK-002` 保持 OPEN；所有新文档写“内部 v4.3.0（文件名 v4.3.1，BLK-002）”。
- 后续：用户 2026-11-08 确认内部 v4.3.0 为内容基线，`v4.3.1` 仅为文件名标签；`BLK-002` 关闭，`C-001` 标 `RESOLVED`。
- 教训：版本判断必须核对封面/页眉/正文/属性/修订记录/文件名，不能只看文件名或 SHA256。

### L-10 DOCX 属性与真实内容可能完全不同

- 现象：`core.xml` 的 created/modified 是 `2013-12-23T23:15:00Z`，`app.xml` 的 `Pages=1`、`Words=0`，而文档控制表写 `2026 年 11 月 6 日`，正文 754 段、80 表。
- 原因：文档由 `python-docx` 生成，属性是模板残留；没有用 Word 重新保存/分页。
- 处理：日期引用文档控制表/文件系统；页数标注“不可用”；不把属性值当证据。
- 教训：DOCX 属性不是可信元数据；涉及日期、页数、作者、修订号时必须与正文/文件系统交叉核对。

### L-11 更宽权限下通过，不等于受限环境可用

- 现象：阶段 7 的 23 项测试在 `workspace-write` 下全部于 setUp 阶段失败（43 个 `PermissionError [WinError 5]`，无断言失败）；阶段 8 用户切换为 `danger-full-access` 后，同一套测试 23/23 OK（3.2 s）。
- 风险：把“全权限下通过”写成“workspace-write 已验证”，会把环境阻塞掩盖成代码通过。
- 处理：阶段 8 把 `BLK-003` 保持 `OPEN`；全权限日志只作为“权限足够时可运行”的证据，不作为 workspace-write 验收依据；未改测试、expected 或临时目录位置。
- 2026-11-08 恢复 `workspace-write` 后按用户命令取证：`tempfile.mkdtemp(dir=D:\ResearchFlow-project)` 能创建目录，但写 `probe.txt` 抛 `PermissionError [Errno 13]`，路径 `D:\ResearchFlow-project\tmpavet2qv9\probe.txt`。DSH 权限诊断结论 `NOT_THIS_CLASS`：`WRITE_DAC` / `WRITE_OWNER` 均具备，`FIXED=0`；机制为沙箱授权未向运行期新建子目录传播，属环境侧问题，不是仓库 ACL 损坏。`BLK-003` 保持 OPEN / MEDIUM；不得手工改 ACL、不得重复诊断；13b 维持 NOT VERIFIED。
- 教训：测试结论必须绑定运行时的权限/沙箱条件；权限提升只能排除代码缺陷，不能证明受限环境可用；遇到 ACL 异常先取证，不先改测试或放宽权限；诊断结论要区分“环境授权传播问题”与“仓库权限损坏”。
