[P0015] <heading 1> HEADING(outline=None)
    摘要
[P0016] <(none)> 
    ResearchFlow 3.1 面向高校 AI 实验复现与核查场景，建设具备多智能体协作、DAG 工作流编排、运行期动态调度、故障恢复、知识反馈和独立结果验证能力的平台。项目关注的核心问题不是 Agent 能否生成一份看似完整的实验报告，而是系统能否证明任务确实执行、结果符合预先定义的规则，并允许第三方在隔离环境中复核。
[P0017] <(none)> 
    平台采用“Agent 决策面 + 确定性控制面 + 受控执行面 + 独立证据/验证面”的架构。六个逻辑 Agent 负责规划、数据理解、实验执行请求、结果分析、故障恢复提案与验证计划；它们不直接写任务状态、证据库或签名私钥。StateMachine 是状态变更唯一入口；Executor 运行审核过的内置模板；Collector 监听执行事件并追加 E0/E1/E2 证据；独立 Verifier 执行 L1/L2/L3 检查并签发报告与完成凭证。
[P0018] <(none)> 
    三条核心技术主线：① EG + TLV：以证据门控和三级验证把完成声明转换为可复核判定；② DC + SPA：识别限定条件下的确定性节点，并为合法跳过重执行生成可审计的省略溯源凭证；③ Scheduler + Governor + VAS：根据依赖、风险、资源和验证预算动态安排执行与验证。六角色协作、知识库、FOL 三层反馈环、Harness Adapter 和 ResearchFlow-Bench 构成支撑体系。
[TABLE 04] rows=1 cols~=1
  R01: 一句话记忆点 ⏎ ResearchFlow 把“Agent 说自己完成了”变成“独立验证器根据真实执行证据签发、第三方可以离线复核的完成凭证”。

    1.1 一句话定位
[P0026] <(none)> 
    ResearchFlow 3.1 是面向 AI 实验任务的可信多智能体编排、动态调度与独立验证平台。它不是通用聊天助手，也不是单纯实验追踪器，而是把任务规划、执行控制、证据采集、故障恢复、结果验证和凭证签发整合为一条可审计工程链。
[P0027] <(none)>

[P0055] <heading 2> HEADING(outline=None)
    3.1 核心判定对象
[P0056] <(none)> 
    将一次实验表示为 G=(V,E)，V 为任务节点，E 为依赖边；任务目标 g、执行轨迹 τ、Agent 声明 δ、证据集合 𝓔、规则版本 ρ、环境指纹 φ。
[P0057] <(none)> 
    VERIFY(g, G, τ, δ, 𝓔, ρ, φ) → {VERIFIED, PARTIAL, FAILED, BLOCKED}
[P0058] <(none)> 
    声明 δ 只提供待核查主张，不构成成功证据。只有符合规则的 E2/E3 证据、链校验、规则版本、无未解释冲突和所需 L3 覆盖共同成立时，报告才允许为 VERIFIED。
[P0059] <heading 2> HEADING(outline=None)
    3.2 虚假完成的七种形态
[TABLE 14] rows=8 cols~=4
  R01: 编号 | 形态 | 典型表现 | 检测机制
  R02: F-1 | 未执行 | 只输出“训练完成”，无本次执行事件与产物。 | E2 必检项缺失、L1。
  R03: F-2 | 部分执行冒充全量 | 只训练一个模型，却报告多个模型。 | 配置/产物集合一致性。
  R04: F-3 | 旧结果复用 | 上次 metrics、模型或预测文件冒充本次。 | 任务/数据/代码/环境指纹。
  R05: F-4 | 篡改/成套伪造 | 改结果并重算普通哈希，或伪造 predictions 与 metrics。 | L1、L2、L3。
  R06: F-5 | 口径错误/泄漏 | 训练集冒充测试集、测试集调参、分组/时间泄漏。 | L2 五规则、Split Manifest、L3。
  R07: F-6 | 协议/权限违规 | 引用不存在 evidence_id、越权写库或调用未注册工具。 | 消息 Schema、Tool Gateway、权限审计。
  R08: F-7 | 资源/运行异常 | 超时、内存超限、子进程残留、依赖不一致。 | Governor、Executor 事件、进程树回收。

[P0065] <heading 2> HEADING(outline=None)
    3.5 三个可靠性命题
[P0066] <List Bullet> 
    条件性可信：若必检规则是任务完成必要条件，E2/E3 由非 Agent 组件产生，链与签名有效，且指标来源节点经 L3 重跑，则 VERIFIED 对已定义的 F-1 至 F-5 具备可审查拒绝能力；该命题依赖 Executor、Collector、Verifier 与规则集处于信任边界内。
[P0067] <List Bullet> 
    不完备性：规则不能穷尽未知攻击；真实任务也可能因环境差异被误拒。必须报告误拒率、未知差异和人工申诉，不宣称零漏检。
[P0068] <List Bullet> 
    安全剪枝：仅当节点具备有效 DC、输入/前驱指纹未变、磁盘产物复验通过、当前规则仍通过且节点无副作用时，才允许 SPA；否则保守重跑。

[P0077] <heading 2> HEADING(outline=None)
    4.3 统计纪律
[P0078] <List Bullet> 
    任务是统计单位；同一任务多次重复不能当独立样本。重复先在任务内聚合，再做任务级推断。
[P0079] <List Bullet> 
    正常/一般异常任务每方案至少 3 次重复；随机性实验使用预先固定种子；报告 pass@3 与 pass^3。
[P0080] <List Bullet> 
    比例指标用精确二项区间；零错误必须同时报告分母、上界和盲测构造方式。
[P0081] <List Bullet> 
    配对二值比较用 McNemar；连续配对比较用任务级 bootstrap；多重比较采用 Holm 校正或标为探索性。
[P0082] <List Bullet> 
    预注册任务、故障、规则、等价区间和统计脚本；正式运行后不得悄悄改规则。
[P0083] <List Bullet> 
    负面结果、失败案例、未知差异和降级动作必须保留。
[P0084] <heading 2> HEADING(outline=None)
    4.4 明确不做
[P0085] <List Bullet> 
    不做通用科研助手；首期只覆盖可机器验证的表格型 ML 实验。
[P0086] <List Bullet> 
    不做 GPU 集群、分布式执行、多机高可用。
[P0087] <List Bullet> 
    不执行 Agent 或用户生成的任意不可信代码，只运行审核过的内置模板。
[P0088] <List Bullet> 
    不宣称跨硬件/跨版本普遍复现；首期目标为同软件环境下独立重执行。
[P0089] <List Bullet> 
    不宣称哈希链绝对不可篡改；只称可发现篡改，并明确密钥与锚定边界。
[P0090] <List Bullet> 
    不把知识检索、Agent 自评或多 Agent 投票当作实验完成证据。

    7.5 JCS + Ed25519 规范
[P0174] <List Bullet> 
    签名载荷用 RFC 8785 JCS 生成规范化 UTF-8 字节串，再添加对象类型域分离前缀并用 Ed25519（RFC 8032）签名。
[P0175] <List Bullet> 
    JCS 递归排序 JSON 对象属性名；数组元素顺序必须保持原样，数组内对象属性仍递归规范化。不得把数组整体按字典序重排。
[P0176] <List Bullet> 
    拒绝重复键、NaN、Infinity 和非法 Unicode；时间统一 RFC 3339 UTC；数值字段采用明确 Schema 类型与精度。
[P0177] <List Bullet> 
    签名字段采用版本化白名单；未知字段不得静默纳入或忽略；Schema 升级必须提高版本号。
[P0178] <List Bullet> 
    公钥不作为自证信任来源；验签工具预置可信指纹/信任根。域分离前缀分别用于 Report、Certificate、DC、SPA。

[P0188] <heading 1> HEADING(outline=None)
    第8章  核心机制二：DC、SPA、安全恢复与动态调度
[P0189] <heading 2> HEADING(outline=None)
    8.1 四个决策组件
[P0190] <(none)> 
    动态调度拆成四个可独立实现的组件：Ready Scheduler 决定 READY 节点执行顺序；Governor 决定并发和资源水位；Recovery 决定失败后哪些节点失效、哪些必须重跑；VAS 决定有限验证预算投向哪些验证项。DC/SPA 是 Recovery 的安全剪枝依据，不替代 Scheduler。
[P0191] <heading 2> HEADING(outline=None)
    8.2 DC：确定性资格凭证
[P0192] <(none)> 
    DC 不是数学意义上的普遍确定性证明，而是对某节点类型、固定输入结构、代码版本、依赖锁、环境指纹和规则版本，在受控条件下观察到 k 次跨进程、跨目录 bit-exact 一致的经验性资格。仅纯函数、无外部副作用、输入可完整枚举的节点可申请。
[TABLE 34] rows=7 cols~=3
  R01: 条件 | 要求 | 不满足时
  R02: 节点纯度 | 无数据库写入、网络请求、全局状态修改、当前时间/随机外部源依赖。 | 永不签 DC。
  R03: 输入固定 | 数据、配置、代码、模板、依赖与上游哈希一致。 | DC 失效。
  R04: 环境指纹 | OS/架构/CPU、Python、依赖锁、关键库、线程变量、locale/timezone、种子策略。 | 环境变化即失效。
  R05: 重复执行 | 默认 k=3 独立进程/目录；敏感因素增加探针。 | 任一产物/指标不 bit-exact，不签 DC。
  R06: 随机性节点 | 预期具有随机波动的训练/采样节点不签 DC。 | 用多种子/TOST 评估，不允许 DC 剪枝。
  R07: 有效期 | DC 带 expires_at、ruleset_hash、code_hash、input_schema_hash。 | 到期/规则变更后重新评估。

[TABLE 35] rows=1 cols~=1

[P0201] <heading 2> HEADING(outline=None)
    8.4 定向恢复算法
[P0202] <(none)> 
    plan_recovery(graph, failed_node):
[P0203] <(none)> 
      affected = descendants(failed_node) ∪ {failed_node}
[P0204] <(none)> 
      for node in topological_order(affected):
[P0205] <(none)> 
          if node == failed_node or not retryable(node): retry_or_escalate()
[P0206] <(none)> 
          elif has_side_effect(node): reexecute()
[P0207] <(none)> 
          elif not evidence_valid(node): reexecute()
[P0208] <(none)> 
          elif not predecessor_hashes_unchanged(node): reexecute()
[P0209] <(none)> 
          elif not valid_DC(node, current_env): reexecute()
[P0210] <(none)> 
          elif not disk_rehash_matches(node): reexecute()
[P0211] <(none)> 
          elif not gate_passes_under_current_rules(node): reexecute()
[P0212] <(none)> 
          else: sign_SPA(node, all_checks)
[P0213] <(none)> 
      return immutable_plan
[P0214] <(none)> 
    恢复计划在执行前冻结；先算受影响子图再执行，避免运行中上游变化造成剪枝判据前后不一致。未持有 DC 的节点一律保守重跑。
[P0215] <heading 2> HEADING(outline=None)

[P0216] <(none)> 
    只在依赖满足且资源允许的 READY 节点中选择下一执行对象。建议初始评分：
[P0217] <(none)>

[P0221] <heading 2> HEADING(outline=None)
    8.7 VAS 验证感知调度
[P0222] <(none)> 
    VAS 把验证预算作为显式资源。风险分数由预注册特征构成：
[P0223] <(none)> 
    R_i = 0.25·F_i + 0.20·N_i + 0.20·G_i + 0.20·I_i + 0.15·A_i
[P0224] <(none)> 
    F 为历史失败风险（Beta-Binomial 平滑）；N 为输入/配置新颖度；G 为证据缺口；I 为下游/报告影响；A 为异常信号。特征归一化到 [0,1]，权重在 G-dev 校准后、G-hold 前冻结。
[P0225] <(none)> 
    Utility_i = R_i × CoverageBenefit_i
[P0226] <(none)> 
    Priority_i = Utility_i / max(EstimatedCost_i, ε)
[P0227] <(none)> 
    maximize Σ Utility_i·x_i   subject to Σ Cost_i·x_i ≤ Budget
[P0228] <(none)> 
    x_i = 1 for mandatory verification nodes
[P0229] <(none)> 
    强制集合至少包括最终报告节点、报告指标来源节点、证据完整性异常节点和安全关键节点。强制节点不得被预算优化排除。节点少时用动态规划求精确解；节点多时可用贪心近似，并报告相对小规模最优解的差距。
[P0230] <heading 2> HEADING(outline=None)

    17.1 安全边界
[P0427] <(none)> 
    MVP 的安全边界是审核过的内置模板、参数化输入、受限工作目录、进程资源治理和写入者隔离，不是任意代码安全沙箱。首期不执行外部代码、不允许运行期安装依赖、不开放默认网络。未来开放用户代码时必须增加容器/microVM、只读数据挂载、网络出口策略、CPU/内存/磁盘/进程限制和供应链审计。
[P0428] <heading 2> HEADING(outline=None)
    17.2 数据伦理
[P0429] <List Bullet>

[P0430] <List Bullet>

[P0431] <List Bullet> 
    不判断学生是否使用 AI，不输出 AI 作弊概率；只判断实验过程和证据是否符合公开规则。
[P0432] <List Bullet>

[P0433] <List Bullet>

[P0686] <heading 2> HEADING(outline=None)
    H.3 高概率答辩问题
[TABLE 75] rows=9 cols~=2
  R01: 问题 | 建议回答结构
  R02: 你们与 Agent Harness 有什么不同？ | Harness 提供通用运行时；ResearchFlow 是实验领域质量控制层，重点是 E2/E3、L3、证据门控、恢复剪枝与离线凭证。
  R03: 哈希链是否能防止所有篡改？ | 不能。它提高篡改可发现性；完全控制主机、密钥和锚定位置的攻击者不在 MVP 威胁模型内。
  R04: 为什么还要 L3？ | L1 检查完整，L2 检查自洽；成套伪造可同时通过两者，L3 在新目录从原始数据真实重跑。
  R05: 为什么不是所有节点都重跑？ | 成本较高；仅对符合严格 DC 条件的纯节点考虑 SPA，所有剪枝都有证明，无 DC 保守重跑。
  R06: DC 是否证明确定性？ | 不是普遍证明，只是限定节点类型、输入、代码、依赖和环境下的经验性资格。
  R07: VAS 会不会漏掉高风险项？ | 强制验证集合不可被预算优化排除；VAS 只排序可选验证项，并用同预算实验对比。
  R08: 项目是否能在普通电脑运行？ | 首期按单机、16GB、无 GPU、并发 2、内置表格 ML 模板设计；最终以目标设备实测报告为准。
  R09: AI 会不会自己编造证据？ | Agent 没有证据库写权限；E2 来自 Collector，E3 来自独立 Verifier，凭证由 Verifier 签名。
