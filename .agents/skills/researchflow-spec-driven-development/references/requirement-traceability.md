# 需求追踪与验收条件参考

> 状态：方法参考，不是已冻结 PRD。FR-001–FR-020 的具体内容**待核实**，必须从正式需求文档或用户书面指令补齐。

## 1. 追踪表字段

| 字段 | 说明 | 必填 |
|---|---|---|
| `req_id` | 稳定编号，如 `FR-001`；未定义时用 `CAND-xxx` | 是 |
| `source` | 用户指令 / 策划书章节 / PRD / ADR / 外部资料 | 是 |
| `source_quote` | 原文摘要或短引用，不改变原意 | 是 |
| `requirement` | 可验证的需求陈述 | 是 |
| `priority` | `P0` / `P1` / `P2` / `待确认` | 是 |
| `phase` | `WORKSTATION_SETUP` / `G0` / `T0` / `T1` / `T2` | 是 |
| `module` | 规划、执行、证据、验证、工作台等 | 是 |
| `depends_on` | 其他需求、契约、环境或批准 | 是 |
| `risks` | 技术、数据、安全、进度风险 | 是 |
| `acceptance` | 可观察的验收条件 | 是 |
| `evidence` | 预期证据类型/路径 | 是 |
| `status` | `DRAFT` / `PROPOSED` / `APPROVED` / `IN_PROGRESS` / `DONE` / `DEFERRED` | 是 |
| `notes` | 待核实、冲突、假设 | 否 |

## 2. FR 映射协议

1. 只映射已有正式定义的 FR；不要为了凑满 FR-001–FR-020 编造条目。
2. 一个需求可以映射多个 FR，但必须说明拆分理由。
3. 一个 FR 可以被多个需求引用，但验收条件必须一致。
4. 未定义的 FR 写 `待定义`，并在 `source` 标“无正式来源”。
5. 发现 FR 冲突时停止，提交冲突表和需要用户裁决的问题。

## 3. 用户故事格式

```text
作为 <角色>，
我希望 <能力>，
以便 <可观察的价值>。

验收条件：
- AC-1（正例）：
- AC-2（负例）：
- AC-3（边界）：
```

## 4. 验收条件质量检查

| 检查项 | 不合格示例 | 合格示例 |
|---|---|---|
| 可观察 | “体验良好” | “提交 10 个节点后，API 在 2 秒内返回 201，且返回 task_id” |
| 可测试 | “支持恢复” | “杀死进程后重启，RUNNING 节点进入 RECOVERING，未完成 attempt 不被标 COMPLETED” |
| 有边界 | “处理输入” | “空字符串返回 422；长度 1–255 通过；256 返回 422” |
| 有负例 | 只写成功路径 | “E0 声明不能使 Gate PASS；返回 GAP 并列出缺失项” |
| 有来源 | “用户说要快” | “来源：用户 2026-11-08 指令；策划书 §15.2” |

## 5. 非功能需求清单

- 运行环境：Windows 11 单机、16GB 内存、CPU-only。
- 并发上限 2；未实测前不得宣称达成。
- 不执行任意用户代码；不默认开放网络；不强制 Docker；不部署本地大模型。
- 解释器：Python 3.11.16（64 位）绝对路径。
- 审计：状态迁移、证据写入、权限拒绝可追溯。
- 安全：秘密不进代码/日志/证据包；最小权限；数据最小化。
- 可复现：命令、版本、数据哈希、日志路径齐全。

## 6. 审批触发条件

- 跨模块接口变化。
- Schema / 数据库 / 状态机变化。
- 安全边界、权限、密钥、信任锚变化。
- 已冻结架构或规格变化。
- 范围扩展到 T1/T2、LLM、Agent、Harness Adapter。
- 新增依赖或改变解释器基线。
